# Portal JSON API, version 1

This is the contract for the self-service portal API at `/api/v1`. All stages of
`docs/plans/onboarding-and-eap-tls.md` build against it. Stage S0 implements the
rules, the token endpoint and `GET /me` (`portal/apiauth.py`). The other stages
implement the endpoints that are marked with their stage.

Do not change a request or response shape here without a new version (`/api/v2`).
You can add a new optional field to a response. Clients must ignore fields that
they do not know.

| Stage | Module | Endpoints |
|---|---|---|
| S0 | `apiauth.py` | `POST /auth/token`, `GET /me` |
| S1 | `api.py` | `GET /devices`, `POST /devices/disconnect`, `POST /password` |
| S2 | `activity.py` | `GET /activity`, `GET /alerts`, `POST /alerts/{mac}` |
| S3 | `downloads.py` | `GET /profiles/android` |
| S5 | `pki.py` | `POST /certs`, `GET /certs`, `DELETE /certs/{serial}` |
| S6 | `downloads.py`, `pki.py` | `GET /profiles/android?method=tls` |

## 1. General rules (all endpoints)

### 1.1 Transport and format
- The base path is `/api/v1`. All paths below are relative to it.
- Request and response bodies are JSON (UTF-8). The largest request body is 16 KB
  (`MAX_CONTENT_LENGTH`). A larger body gets `413`.
- `POST`, `PUT` and `PATCH` must send `Content-Type: application/json`. Another
  content type gets `415` before any other check. `GET` and `DELETE` send no body.
- Times are ISO 8601 strings with a UTC offset, for example
  `"2026-10-26T18:25:07+05:30"`. The offset is the database time zone (`TZ`).
- A MAC address is a string in the form that the access point sends in
  `Calling-Station-Id`, for example `"DE-AD-BE-EF-00-01"`. Send it back exactly as
  you received it. The server accepts `[0-9A-Za-z:.-]{1,40}`.
- A field with no value is `null`. It is never left out.

### 1.2 Authentication
- `POST /auth/token` is the only endpoint without a token.
- All other endpoints need the header `Authorization: Bearer <access_token>`.
- The API does not use the session cookie of the web portal. A request with a
  cookie and no `Authorization` header gets `401`. An API response never sets a cookie.
- On every call the server reads the account from LDAP again. The token stops
  working at once when:
  - the password changes (the entry version, `entryCSN`, changes);
  - an administrator disables the account (group `disabled`);
  - the account leaves all Wi-Fi groups, or is deleted.
- A token lives `API_TOKEN_MINUTES` minutes (default 15, allowed 1 to 30). It never
  lives longer than 30 minutes after issue. There is no refresh token: when a call
  gets `401`, the client asks for the password and logs in again. The client keeps
  the token in memory only. It never stores the password.
- There is no logout endpoint, because the server keeps no list of tokens. To log
  out, the client forgets the token. A web logout does not end API tokens. To end
  all tokens of a user at once, change the password or disable the account.
- The token is an opaque string. Clients must not read or change it.
  (Server side: itsdangerous `URLSafeTimedSerializer`, key `PORTAL_SECRET_KEY`,
  salt `api-v1`, payload `uid`, `dn`, `ver` (entryCSN), `iat`, `exp`.)

### 1.3 Browser rules
- No CSRF token is needed: a browser never sends the `Authorization` header by
  itself, and a cookie alone is refused.
- The CSRF rule follows the path, not the view (`app.csrf_for_web`): every form
  outside `/api` needs a CSRF token, and nothing under `/api` does. The API
  decorators refuse to serve a view outside `/api` (`500 server_error`).
- The server sends no CORS headers (`Access-Control-*`). A web page on another
  site cannot read API responses.
- Every response has `Cache-Control: no-store` and the same
  `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options` and
  `Referrer-Policy` headers as the web pages.

### 1.4 Errors
Every error response has this body:

```json
{"error": {"code": "login_failed", "message": "Login failed. Check your ID and password, then try again."}}
```

- `code` is stable. Clients use it to decide what to do.
- `message` is English text that is safe to show to the user. It can change.

| Status | Codes | Meaning |
|---|---|---|
| 400 | `invalid_input`, `password_refused`, `bad_csr` | The request is not valid. |
| 401 | `unauthorized`, `login_failed` | No token, bad or expired token, account changed; or wrong login. The `401` for a token also has `WWW-Authenticate: Bearer realm="api"`. |
| 403 | `wrong_password` | The current password is wrong (password change). |
| 404 | `not_found` | No such path, or no such object of this user. |
| 405 | `method_not_allowed` | Wrong HTTP method for the path. |
| 409 | `conflict`, `disconnect_in_progress`, `cert_limit` | The request conflicts with the current state. |
| 413 | `too_large` | The body is larger than 16 KB. |
| 415 | `unsupported_media_type` | A write without `Content-Type: application/json`. |
| 429 | `rate_limited` | Too many attempts or calls. Wait, then try again. Any endpoint with a token can give it (`API_CALLS`, section 1.5). |
| 500 | `server_error` | A fault in the server, for example an API view on a path outside `/api`. |
| 503 | `unavailable`, `busy` | LDAP, PostgreSQL or the login service is not available, or too many logins are in progress. Try again later. |

### 1.5 Rate limits
The API uses the same limiter objects as the web portal (`portal/app.py`), in the
same process. One limit covers both front ends:

| Limiter | Limit | Key | Used by |
|---|---|---|---|
| `LOGIN_BY_USER` | 5 per 15 min | (uid, client IP) | web login, `POST /auth/token` |
| `LOGIN_BY_IP` | 20 per 15 min | client IP | web login, `POST /auth/token` |
| `LOGIN_SLOTS` | 4 logins at the same time | - | web login, `POST /auth/token` |
| `PASSWORD_BY_USER` | 5 wrong current passwords per 15 min | uid | web `/password`, `POST /password` |
| `DISCONNECTS` | 5 per 5 min, 1 at a time | uid | web Disconnect, `POST /devices/disconnect`, `POST /alerts/{mac}` with `not_me` |
| `API_CALLS` | 60 per min | uid | every endpoint with a token (API only) |

A successful login takes the failed attempts back, as on the web.

`API_CALLS` counts every call with a valid token, before the LDAP check: each
call costs LDAP searches on the one portal connection that logins also use. A
client that polls must stay below 1 call per second.

## 2. S0: login and account

### `POST /auth/token`
Request:
```json
{"uid": "student042", "password": "..."}
```
Both fields must be strings, or the answer is `400 invalid_input`. The server
removes spaces at the start and end of `uid`.

Response `200`:
```json
{
  "access_token": "eyJ1aWQiOi...",
  "token_type": "Bearer",
  "expires_in": 900,
  "user": {"uid": "student042", "student": true, "device_limit": 3}
}
```
- `expires_in` is in seconds.
- `user.uid` is the uid as stored in LDAP (it can differ in case from the typed one).
- `user.device_limit` is the number of devices that the user can have online at
  the same time, or `null` for no limit (not a student, or `DEVICE_LIMIT_STUDENTS=0`).

Errors: `400 invalid_input`, `401 login_failed`, `429 rate_limited`,
`503 unavailable`, `503 busy`. All failures of the uid or password give the same
`401` and the same message, as the web login does. A `429` also has that message.

### `GET /me`
Response `200`:
```json
{"uid": "student042", "student": true, "device_limit": 3}
```
Errors: `401 unauthorized`, `503 unavailable`.

## 3. S1: devices and password (`portal/api.py`)

### `GET /devices`
The same data as the web page `/devices` (`app.device_overview`).

Response `200`:
```json
{
  "online": 2,
  "device_limit": 3,
  "reauth_interval": 300,
  "slots": [
    {
      "mac": "DE-AD-BE-EF-00-02",
      "joined": "2026-10-26T11:40:00+05:30",
      "over_limit": false,
      "session": {
        "access_point": "AP-615",
        "ip": "10.10.0.20",
        "started": "2026-10-26T11:40:00+05:30",
        "updated": "2026-10-26T11:50:00+05:30",
        "bytes_up": 2048,
        "bytes_down": 4096
      }
    }
  ],
  "known": [
    {"mac": "DE-AD-BE-EF-00-01", "first_seen": "...", "last_seen": "...", "online": true}
  ],
  "limit_events": [
    {"time": "...", "mac": "DE-AD-BE-EF-00-03", "live_devices": 3, "device_limit": 3, "mode": "soft"}
  ]
}
```
- `slots` is in joining order. `over_limit` is `true` for a slot past `device_limit`.
- `session` is the newest live session of the device. `bytes_up` is
  `acctinputoctets`, `bytes_down` is `acctoutputoctets`.
- `known` is newest `last_seen` first. `limit_events` is the 10 newest, newest first.
  `mode` is `"soft"` (let in, logged only) or `"enforce"` (refused).

Errors: `401`, `503 unavailable`.

### `POST /devices/disconnect`
Request:
```json
{"mac": "DE-AD-BE-EF-00-01"}
```
Sends an RFC 5176 Disconnect-Request for each live session of this user's device
(`app.disconnect_core`).

Response `200`:
```json
{"mac": "DE-AD-BE-EF-00-01", "results": [{"nas": "10.89.0.1", "result": "ACK"}]}
```
`result` is `"ACK"`, `"NAK"` or `"none"` (no reply). With `NAK` or `none`, the
device is dropped at the next re-check, within `reauth_interval` seconds.

Errors: `400 invalid_input` (MAC format), `404 not_found` (no live session of this
user for that MAC), `409 disconnect_in_progress`, `429 rate_limited`,
`503 unavailable`.

### `POST /password`
Request:
```json
{"old": "...", "new": "..."}
```
Calls `app.password_core(uid, dn, old, new, confirm=new)`. The rules are the same
as on the web: 15 to 128 characters, not the uid, not in the blocklist.

Response `204`, no body. The account version changes, so this token and all
other tokens and web sessions of the user end. The client logs in again with
the new password. When `ALLOW_PEAP=yes`, PEAP no longer works for the account.

Errors: `400 invalid_input` (a rule, with the rule text as `message`),
`400 password_refused` (the directory refused the change), `403 wrong_password`,
`429 rate_limited`, `503 unavailable`.

## 4. S2: sign-in activity and new-device alerts (`portal/activity.py`)

### `GET /activity?days=7`
`days` is 1 to 30 (default 7). Another value gets `400 invalid_input`. The data
comes from the SQL function `portal_signins(user, days, limit)` (migration 004).

Response `200`:
```json
{
  "days": 7,
  "signins": [
    {"time": "...", "result": "accept", "access_point": "AP-615", "mac": "DE-AD-BE-EF-00-01", "private_mac": true}
  ]
}
```
- Newest first, at most 100 rows.
- `result` is `"accept"` or `"reject"`. `access_point` can be `null`.
- `private_mac` is `true` when the locally administered bit of the MAC is set
  (a phone's private Wi-Fi address).

Errors: `400 invalid_input`, `401`, `503 unavailable`.

### `GET /alerts`
An alert is a device of this user (`user_devices`) first seen in the last 30
days that has no review (`device_reviews`, migration 005).

Response `200`:
```json
{
  "count": 2,
  "alerts": [
    {"mac": "DE-AD-BE-EF-00-01", "first_seen": "...", "last_seen": "...", "online": true, "private_mac": false}
  ]
}
```
Newest `first_seen` first.

Errors: `401`, `503 unavailable`.

### `POST /alerts/{mac}`
Request:
```json
{"verdict": "me"}
```
`verdict` is `"me"` ("This was me") or `"not_me"`.

Response `200`:
```json
{"mac": "DE-AD-BE-EF-00-01", "verdict": "not_me", "disconnect": [{"nas": "10.89.0.1", "result": "ACK"}], "next": "password"}
```
- `"me"`: the device is marked as reviewed. `disconnect` is `null`, `next` is `null`.
- `"not_me"`: the server records the verdict, then disconnects the device if it
  is online (the same rules and limits as `POST /devices/disconnect`). `disconnect`
  is the result list, or `[]` when the device is not online. `next` is
  `"password"`: the client opens the password change.
  From S6, `"not_me"` also revokes the device's certificates.
- A second review of the same MAC replaces the first.

Errors: `400 invalid_input` (verdict or MAC), `404 not_found` (no device of this
user with that MAC), `409 disconnect_in_progress`, `429 rate_limited`,
`503 unavailable`.

## 5. S3: Wi-Fi profiles (`portal/downloads.py`, `portal/profiles.py`)

### `GET /profiles/android`
The settings that the Android app puts into a `WifiEnterpriseConfig`.

Response `200`:
```json
{
  "ssid": "NITS-Lab",
  "eap": "TTLS",
  "phase2": "PAP",
  "identity": "student042",
  "anonymous_identity": "anonymous",
  "domain_suffix_match": "radius.nitsrinagar.lab",
  "alt_subject_match": "DNS:radius.nitsrinagar.lab",
  "ca_pem": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n"
}
```
- `ssid` comes from `WIFI_SSID`. `ca_pem` is the lab root CA
  (CN "NIT Srinagar Lab CA").
- The response never has a password. The device asks the user for it.

Errors: `401`, `503 unavailable` (the CA file cannot be read).

### Web downloads (session cookie, not the API)
`downloads.setup` serves `/setup`: it detects the OS and offers the files below.
Each file has the uid filled in and never a password.

| Path | Platform |
|---|---|
| `/setup/apple.mobileconfig` | iOS, iPadOS, macOS (CMS-signed when `PROFILE_SIGNING=yes`) |
| `/setup/windows.ps1`, `/setup/windows.xml` | Windows |
| `/setup/linux.sh` | Linux (NetworkManager, `nmcli`) |
| `/setup/chromeos.onc` | ChromeOS |

- Each file is a download (`Content-Disposition: attachment`). The `.mobileconfig` has the type
  `application/x-apple-aspen-config`.
- The portal logs each download (uid and kind), never the content.
- With `PROFILE_SIGNING=yes`, the `.mobileconfig` download gets `503` if the signing certificate
  or key cannot be read. The portal never gives an unsigned profile in place of a signed one.
- If the CA file cannot be read, `/setup` and every download get `503`.
- Windows: `TrustedRootCAHash` in the WLAN XML is the SHA-1 thumbprint of the root CA. This is
  not verified on a real laptop yet (SHA-1 or SHA-256).

## 6. S5: device certificates for EAP-TLS (`portal/pki.py`)

A user can have at most 3 active certificates (not revoked, not expired).

### `POST /certs`
Request:
```json
{"csr_pem": "-----BEGIN CERTIFICATE REQUEST-----\n...", "label": "Pixel 8"}
```
- `csr_pem` is a PKCS#10 request, made on the device. The private key never leaves
  the device. The server ignores the subject of the CSR: the certificate has
  CN = uid, Extended Key Usage clientAuth, and 1 year of validity.
- `label` is 1 to 40 characters.

Response `201`:
```json
{
  "serial": "4f1c0e...",
  "label": "Pixel 8",
  "issued_at": "...",
  "not_after": "...",
  "cert_pem": "-----BEGIN CERTIFICATE-----\n...",
  "chain_pem": "-----BEGIN CERTIFICATE-----\n... (Device CA, then root CA)"
}
```
`serial` is lower-case hexadecimal.

Errors: `400 bad_csr` (not a valid CSR, bad signature, or a weak key),
`400 invalid_input` (label), `409 cert_limit` (3 active certificates already),
`401`, `503 unavailable`.

### `GET /certs`
Response `200`:
```json
{
  "limit": 3,
  "certs": [
    {"serial": "4f1c0e...", "label": "Pixel 8", "issued_at": "...", "not_after": "...",
     "revoked_at": null, "revoke_reason": null, "via": "app", "active": true}
  ]
}
```
- Newest first, revoked certificates included.
- `via` is `"app"` (CSR from the Android app) or `"web"` (PKCS#12 from `/certs`).
- `revoke_reason` is `"user"`, `"not_me"` or `"admin"`, or `null`.

Errors: `401`, `503 unavailable`.

### `DELETE /certs/{serial}`
Revokes the certificate and sends a Disconnect-Request for live EAP-TLS sessions
that use it.

Response `200`:
```json
{"serial": "4f1c0e...", "revoked_at": "...", "disconnect": [{"nas": "10.89.0.1", "result": "ACK"}]}
```
A second `DELETE` of a revoked certificate gives `200` with the first `revoked_at`.

Errors: `404 not_found` (no certificate of this user with that serial),
`409 disconnect_in_progress`, `429 rate_limited`, `401`, `503 unavailable`.

### Web pages (session cookie, not the API)
`pki.certs` serves `/certs`: the list, revoke, and a one-time PKCS#12 download
with a passphrase that is shown on the screen once (Apple, Windows, Linux).

## 7. S6: EAP-TLS profile for Android

### `GET /profiles/android?method=tls`
`method` is `ttls` (default, section 5) or `tls`. Another value gets
`400 invalid_input`.

Response `200` for `tls`:
```json
{
  "ssid": "NITS-Lab",
  "eap": "TLS",
  "phase2": null,
  "identity": "student042",
  "anonymous_identity": null,
  "domain_suffix_match": "radius.nitsrinagar.lab",
  "alt_subject_match": "DNS:radius.nitsrinagar.lab",
  "ca_pem": "-----BEGIN CERTIFICATE-----\n..."
}
```
The app makes the key pair and the CSR, calls `POST /certs`, then calls
`setClientKeyEntry` with its key and `cert_pem` (plus `chain_pem`).

## 8. Notes for the stages that build on S0

### 8.1 Feature modules
- `app.register_features()` (end of `portal/app.py`) loads each of these modules
  if its file exists: `apiauth`, `api`, `activity`, `downloads`, `pki`. Each
  module has one Flask Blueprint called `bp`. The Dockerfile copies `*.py`.
- A module imports `app as core` and calls the core functions:
  `core.login_core`, `core.device_overview`, `core.disconnect_core`,
  `core.password_core`. They raise `core.PortalError` subclasses with `status`,
  `code` and `message`. `apiauth.portal_error(exc)` turns one into the error
  response.
- Every view under `/api` must have `@apiauth.api_auth_required`, which sets
  `flask.g.api_user = {"uid", "dn", "version", "student"}`. A view under `/api`
  without it (or `@apiauth.api_public`, only for the token endpoint) is refused
  with `401` (fail closed), for every method. Do not use these decorators on a
  view outside `/api`: it is refused with `500`. Use `apiauth.api_error(status,
  code, message)` for other errors and `apiauth.json_body()` to read a request.
- Web pages use `@core.login_required` and keep CSRF tokens in their forms.

### 8.2 Web endpoint names
`base.html` shows a nav link only when its endpoint exists:

| Endpoint | Path | Link text | Stage |
|---|---|---|---|
| `activity.page` | `/activity` | Sign-in activity | S2 |
| `downloads.setup` | `/setup` | Set up Wi-Fi | S3 |
| `pki.certs` | `/certs` | Device certificates | S5 |

A page adds its own stylesheet with `{% block head %}` in `base.html`. There are
no inline scripts or styles (CSP).

`devices.html` includes `_alerts.html` if it exists (S2). The activity module
gives the template its data through a context processor of `bp`
(`bp.app_context_processor`), for example an `alerts` list.
