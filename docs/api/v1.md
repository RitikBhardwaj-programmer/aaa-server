# Portal JSON API, version 1

This is the contract for the self-service portal API at `/api/v1`. All stages of
`docs/plans/onboarding-and-eap-tls.md` build against it. Stage S0 implements the
rules, the token endpoint and `GET /me` (`portal/apiauth.py`). The other stages
implement the endpoints that are marked with their stage.

Do not change a request or response shape here without a new version (`/api/v2`).
You can add a new optional field to a response. Clients must ignore fields that
they do not know.

| Stage | Module | Endpoints |
|---|---|---|
| S0 | `apiauth.py` | `POST /auth/token`, `GET /me` |
| S1 | `api.py` | `GET /devices`, `POST /devices/disconnect`, `POST /password` |
| S2 | `activity.py` | `GET /activity`, `GET /alerts`, `POST /alerts/{mac}` |
| S3 | `downloads.py` | `GET /profiles/android` |
| S5 | `pki.py` | `POST /certs`, `GET /certs`, `DELETE /certs/{serial}` |
| S6 | `downloads.py`, `pki.py` | `GET /profiles/android?method=tls` |

## 1. General rules (all endpoints)

### 1.1 Transport and format
- The base path is `/api/v1`. All paths below are relative to it.
- Request and response bodies are JSON (UTF-8). The largest request body is 16 KB
  (`MAX_CONTENT_LENGTH`). A larger body gets `413`.
- `POST`, `PUT` and `PATCH` must send `Content-Type: application/json`. Another
  content type gets `415` before any other check. `GET` and `DELETE` send no body.
- Times are ISO 8601 strings with a UTC offset, for example
  `"2026-10-26T18:25:07+05:30"`. The offset is the database time zone (`TZ`).
- A MAC address is a string in the form that the access point sends in
  `Calling-Station-Id`, for example `"DE-AD-BE-EF-00-01"`. Send it back exactly as
  you received it. The server accepts `[0-9A-Za-z:.-]{1,40}`.
- A field with no value is `null`. It is never left out.

### 1.2 Authentication
- `POST /auth/token` is the only endpoint without a token.
- All other endpoints need the header `Authorization: Bearer <access_token>`.
- The API does not use the session cookie of the web portal. A request with a
  cookie and no `Authorization` header gets `401`. An API response never sets a cookie.
- On every call the server reads the account from LDAP again. The token stops
  working at once when:
  - the password changes (the entry version, `entryCSN`, changes);
  - an administrator disables the account (group `disabled`);
  - the account leaves all Wi-Fi groups, or is deleted.
- A token lives `API_TOKEN_MINUTES` minutes (default 15, allowed 1 to 30). It never
  lives longer than 30 minutes after issue. There is no refresh token: when a call
  gets `401`, the client asks for the password and logs in again. The client keeps
  the token in memory only. It never stores the password.
- There is no logout endpoint, because the server keeps no list of tokens. To log
  out, the client forgets the token. A web logout does not end API tokens. To end
  all tokens of a user at once, change the password or disable the account.
- The token is an opaque string. Clients must not read or change it.
  (Server side: itsdangerous `URLSafeTimedSerializer`, key `PORTAL_SECRET_KEY`,
  salt `api-v1`, payload `uid`, `dn`, `ver` (entryCSN), `iat`, `exp`.)

### 1.3 Browser rules
- No CSRF token is needed: a browser never sends the `Authorization` header by
  itself, and a cookie alone is refused.
- The CSRF rule follows the path, not the view (`app.csrf_for_web`): every form
  outside `/api` needs a CSRF token, and nothing under `/api` does. The API
  decorators refuse to serve a view outside `/api` (`500 server_error`).
- The server sends no CORS headers (`Access-Control-*`). A web page on another
  site cannot read API responses.
- Every response has `Cache-Control: no-store` and the same
  `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options` and
  `Referrer-Policy` headers as the web pages.

### 1.4 Errors
Every error response has this body:

```json
{"error": {"code": "login_failed", "message": "Login failed. Check your ID and password, then try again."}}
```

- `code` is stable. Clients use it to decide what to do.
- `message` is English text that is safe to show to the user. It can change.

| Status | Codes | Meaning |
|---|---|---|
| 400 | `invalid_input`, `password_refused`, `bad_csr` | The request is not valid. |
| 401 | `unauthorized`, `login_failed` | No token, bad or expired token, account changed; or wrong login. The `401` for a token also has `WWW-Authenticate: Bearer realm="api"`. |
| 403 | `wrong_password` | The current password is wrong (password change). |
| 404 | `not_found` | No such path, or no such object of this user. |
| 405 | `method_not_allowed` | Wrong HTTP method for the path. |
| 409 | `conflict`, `disconnect_in_progress`, `cert_limit` | The request conflicts with the current state. |
| 413 | `too_large` | The body is larger than 16 KB. |
| 415 | `unsupported_media_type` | A write without `Content-Type: application/json`. |
| 429 | `rate_limited` | Too many attempts or calls. Wait, then try again. Any endpoint with a token can give it (`API_CALLS`, section 1.5). |
| 500 | `server_error` | A fault in the server, for example an API view on a path outside `/api`. |
| 503 | `unavailable`, `busy` | LDAP, PostgreSQL or the login service is not available, or too many logins are in progress. Try again later. |

### 1.5 Rate limits
The API uses the same limiter objects as the web portal (`portal/app.py`), in the
same process. One limit covers both front ends:

| Limiter | Limit | Key | Used by |
|---|---|---|---|
| `LOGIN_BY_USER` | 5 per 15 min | (uid, client IP) | web login, `POST /auth/token` |
| `LOGIN_BY_IP` | 20 per 15 min | client IP | web login, `POST /auth/token` |
| `LOGIN_SLOTS` | 4 logins at the same time | - | web login, `POST /auth/token` |
| `PASSWORD_BY_USER` | 5 wrong current passwords per 15 min | uid | web `/password`, `POST /password` |
| `DISCONNECTS` | 5 per 5 min, 1 at a time | uid | web Disconnect, `POST /devices/disconnect`, `POST /alerts/{mac}` with `not_me` |
| `API_CALLS` | 60 per min | uid | every endpoint with a token (API only) |
| `CERT_ISSUES` (`pki.ISSUES`) | 10 per hour | uid | `POST /certs`, web `POST /certs/new` (S5) |

A successful login takes the failed attempts back, as on the web.

`API_CALLS` counts every call with a valid token, before the LDAP check: each
call costs LDAP searches on the one portal connection that logins also use. A
client that polls must stay below 1 call per second.

## 2. S0: login and account

### `POST /auth/token`
Request:
```json
{"uid": "student042", "password": "..."}
```
Both fields must be strings, or the answer is `400 invalid_input`. The server
removes spaces at the start and end of `uid`.

Response `200`:
```json
{
  "access_token": "eyJ1aWQiOi...",
  "token_type": "Bearer",
  "expires_in": 900,
  "user": {"uid": "student042", "student": true, "device_limit": 3}
}
```
- `expires_in` is in seconds.
- `user.uid` is the uid as stored in LDAP (it can differ in case from the typed one).
- `user.device_limit` is the number of devices that the user can have online at
  the same time, or `null` for no limit (not a student, or `DEVICE_LIMIT_STUDENTS=0`).

Errors: `400 invalid_input`, `401 login_failed`, `429 rate_limited`,
`503 unavailable`, `503 busy`. All failures of the uid or password give the same
`401` and the same message, as the web login does. A `429` also has that message.

### `GET /me`
Response `200`:
```json
{"uid": "student042", "student": true, "device_limit": 3}
```
Errors: `401 unauthorized`, `503 unavailable`.

## 3. S1: devices and password (`portal/api.py`)

### `GET /devices`
The same data as the web page `/devices` (`app.device_overview`).

Response `200`:
```json
{
  "online": 2,
  "device_limit": 3,
  "reauth_interval": 300,
  "slots": [
    {
      "mac": "DE-AD-BE-EF-00-02",
      "joined": "2026-10-26T11:40:00+05:30",
      "over_limit": false,
      "session": {
        "access_point": "AP-615",
        "ip": "10.10.0.20",
        "started": "2026-10-26T11:40:00+05:30",
        "updated": "2026-10-26T11:50:00+05:30",
        "bytes_up": 2048,
        "bytes_down": 4096
      }
    }
  ],
  "known": [
    {"mac": "DE-AD-BE-EF-00-01", "first_seen": "...", "last_seen": "...", "online": true}
  ],
  "limit_events": [
    {"time": "...", "mac": "DE-AD-BE-EF-00-03", "live_devices": 3, "device_limit": 3, "mode": "soft"}
  ]
}
```
- `slots` is in joining order. `over_limit` is `true` for a slot past `device_limit`.
- `session` is the newest live session of the device. `bytes_up` is
  `acctinputoctets`, `bytes_down` is `acctoutputoctets`.
- `known` is newest `last_seen` first. `limit_events` is the 10 newest, newest first.
  `mode` is `"soft"` (let in, logged only) or `"enforce"` (refused).

Errors: `401`, `503 unavailable`.

### `POST /devices/disconnect`
Request:
```json
{"mac": "DE-AD-BE-EF-00-01"}
```
Sends an RFC 5176 Disconnect-Request for each live session of this user's device
(`app.disconnect_core`).

Response `200`:
```json
{"mac": "DE-AD-BE-EF-00-01", "results": [{"nas": "10.89.0.1", "result": "ACK"}]}
```
`result` is `"ACK"`, `"NAK"` or `"none"` (no reply). With `NAK` or `none`, the
device is dropped at the next re-check, within `reauth_interval` seconds.

Errors: `400 invalid_input` (no `mac` string, or MAC format), `404 not_found` (no live session of this
user for that MAC), `401`, `409 disconnect_in_progress`, `429 rate_limited`,
`503 unavailable`.

### `POST /password`
Request:
```json
{"old": "...", "new": "..."}
```
Calls `app.password_core(uid, dn, old, new, confirm=new)`. The rules are the same
as on the web: 15 to 128 characters, does not contain the uid (any case), not in
the blocklist. The API has no `confirm` field: `new` is also the confirmation.

Response `204`, no body. The account version changes, so this token and all
other tokens and web sessions of the user end. The client logs in again with
the new password. When `ALLOW_PEAP=yes`, PEAP no longer works for the account.
When `pki` is loaded (S5), every active device certificate of the user is revoked with
reason `"password"` (`pki.revoke_all_core`), so a certificate never outlives a stolen
password; each device then sets up its certificate again. A failure there is logged
and never undoes the password change.

Errors: `400 invalid_input` (a rule, with the rule text as `message`),
`400 password_refused` (the directory refused the change), `401`, `403 wrong_password`,
`429 rate_limited`, `503 unavailable`. A rule error is not counted in
`PASSWORD_BY_USER`; a wrong `old` is.

## 4. S2: sign-in activity and new-device alerts (`portal/activity.py`)

### `GET /activity?days=7`
`days` is 1 to 30 (default 7). Another value gets `400 invalid_input`. The data
comes from the SQL function `portal_signins(user, days, limit)` (migration 004).

Response `200`:
```json
{
  "days": 7,
  "signins": [
    {"time": "...", "result": "accept", "access_point": "AA-BB-CC-DD-EE-FF:NITS-Lab",
     "ap_mac": "AA-BB-CC-DD-EE-FF", "ssid": "NITS-Lab", "mac": "DE-AD-BE-EF-00-01", "private_mac": true}
  ]
}
```
- Newest first, at most 100 rows. Only the rows of the token's user.
- `result` is `"accept"` or `"reject"`. `access_point` can be `null`.
- `access_point` is the `Called-Station-Id` as the access point sent it, usually
  `<AP MAC>:<SSID>`. `ap_mac` and `ssid` are its two parts (added fields). When the
  value does not start with a MAC (for example `"AP-615"`), `ap_mac` is the whole
  value and `ssid` is `null`.
- The function `portal_signins` returns only the time, the result, the access
  point and the device MAC. It never returns `Class` or another column of
  `radpostauth`, and the role `portal` cannot read `radpostauth` directly.
- `private_mac` is `true` when the locally administered bit of the MAC is set
  (a phone's private Wi-Fi address).

Errors: `400 invalid_input`, `401`, `503 unavailable`.

### `GET /alerts`
An alert is a device of this user (`user_devices`) first seen in the last 30
days that has no review (`device_reviews`, migration 005).
A review is deleted together with its `user_devices` row (foreign key, `ON DELETE
CASCADE`). So a MAC that the maintenance job forgot (`DEVICE_EXPIRY_DAYS`) gives a
new alert when it comes back.

Response `200`:
```json
{
  "count": 2,
  "alerts": [
    {"mac": "DE-AD-BE-EF-00-01", "first_seen": "...", "last_seen": "...", "online": true, "private_mac": false}
  ]
}
```
Newest `first_seen` first.

Errors: `401`, `503 unavailable`.

### `POST /alerts/{mac}`
Request:
```json
{"verdict": "me"}
```
`verdict` is `"me"` ("This was me") or `"not_me"`.

Response `200`:
```json
{"mac": "DE-AD-BE-EF-00-01", "verdict": "not_me", "disconnect": [{"nas": "10.89.0.1", "result": "ACK"}], "next": "password"}
```
- `"me"`: the device is marked as reviewed. `disconnect` is `null`, `next` is `null`.
- `"not_me"`: the server records the verdict, then disconnects the device if it
  is online (the same rules and limits as `POST /devices/disconnect`). `disconnect`
  is the result list, or `[]` when the device is not online. `next` is
  `"password"`: the client opens the password change.
  From S6, `"not_me"` also revokes the device's certificates.
- A second review of the same MAC replaces the first.
- `{mac}` is a device of the token's user (`user_devices`); any other MAC gets
  `404 not_found`. The verdict is recorded before the disconnect: after a `409` or
  `429` the verdict stays recorded, and the client still opens the password change.
- The web page uses the same rules: `POST /activity/review` (form fields `mac`,
  `verdict`, `csrf_token`). "Not me" redirects to `/password`.

Errors: `400 invalid_input` (verdict or MAC), `404 not_found` (no device of this
user with that MAC), `409 disconnect_in_progress`, `429 rate_limited`,
`503 unavailable`.

## 5. S3: Wi-Fi profiles (`portal/downloads.py`, `portal/profiles.py`)

### `GET /profiles/android`
The settings that the Android app puts into a `WifiEnterpriseConfig`.

Response `200`:
```json
{
  "ssid": "NITS-Lab",
  "eap": "TTLS",
  "phase2": "PAP",
  "identity": "student042",
  "anonymous_identity": "anonymous",
  "domain_suffix_match": "radius.nitsrinagar.lab",
  "alt_subject_match": "DNS:radius.nitsrinagar.lab",
  "ca_pem": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n"
}
```
- `ssid` comes from `WIFI_SSID`. `ca_pem` is the lab root CA
  (CN "NIT Srinagar Lab CA").
- The response never has a password. The device asks the user for it.

Errors: `401`, `503 unavailable` (the CA file cannot be read).

### Web downloads (session cookie, not the API)
`downloads.setup` serves `/setup`: it detects the OS and offers the files below.
Each file has the uid filled in and never a password.

| Path | Platform |
|---|---|
| `/setup/apple.mobileconfig` | iOS, iPadOS, macOS (CMS-signed when `PROFILE_SIGNING=yes`) |
| `/setup/windows.ps1`, `/setup/windows.xml` | Windows |
| `/setup/linux.sh` | Linux (NetworkManager, `nmcli`) |
| `/setup/chromeos.onc` | ChromeOS |

- Each file is a download (`Content-Disposition: attachment`). The `.mobileconfig` has the type
  `application/x-apple-aspen-config`.
- The portal logs each download (uid and kind), never the content.
- With `PROFILE_SIGNING=yes`, the `.mobileconfig` download gets `503` if the signing certificate
  or key cannot be read. The portal never gives an unsigned profile in place of a signed one.
- If the CA file cannot be read, `/setup` and every download get `503`.
- Windows: `TrustedRootCAHash` in the WLAN XML is the SHA-1 thumbprint of the root CA. This is
  not verified on a real laptop yet (SHA-1 or SHA-256).

## 6. S5: device certificates for EAP-TLS (`portal/pki.py`)

A user can have at most 3 active certificates (not revoked, not expired). App and web
certificates count in the same limit. The count and the INSERT run in one transaction under a
per-user PostgreSQL advisory lock (`pg_advisory_xact_lock(pki.LOCK_NAMESPACE, hashtext(uid))`),
so parallel requests cannot pass the limit together.

Every certificate is signed by the **Device CA** (`certs/device-ca.pem`, an intermediate under the
lab root with `pathlen:0`; the portal never has the root key) and has:
- subject `CN=<uid>`: the uid as stored in LDAP, nothing else. The subject and the extensions of a
  CSR are ignored; only its public key is used;
- Extended Key Usage `clientAuth` only; Key Usage `digitalSignature` (critical); Basic
  Constraints `CA:FALSE` (critical);
- validity from the moment of issue (`issued_at`) for 365 days (`not_after`);
- a random serial of 20 bytes, sent as 40 lower-case hexadecimal digits: the same form as
  FreeRADIUS's `TLS-Client-Cert-Serial`.

### `POST /certs`
Request:
```json
{"csr_pem": "-----BEGIN CERTIFICATE REQUEST-----\n...", "label": "Pixel 8"}
```
- `csr_pem` is a PEM PKCS#10 request, made on the device. The private key never leaves
  the device. The server checks the signature of the request (proof that the device holds the key).
- Accepted keys: RSA with 2048 to 8192 bits and a public exponent of at least 65537, or EC on
  P-256 or P-384. Any other key (RSA below 2048, P-521, secp256k1, Ed25519, DSA, ...) is `bad_csr`.
- `label` is 1 to 40 characters after spaces at the start and end are removed, with no control or
  format characters. The response gives the stored (stripped) label.

Response `201`:
```json
{
  "serial": "4f1c0e...",
  "label": "Pixel 8",
  "issued_at": "2026-10-27T14:52:01+05:30",
  "not_after": "2027-10-27T14:52:01+05:30",
  "cert_pem": "-----BEGIN CERTIFICATE-----\n...",
  "chain_pem": "-----BEGIN CERTIFICATE-----\n... (Device CA, then root CA)"
}
```

Errors: `400 invalid_input` (`csr_pem` or `label` not a string, or a bad label),
`400 bad_csr` (not a valid CSR, bad signature, or a weak or unknown key),
`409 cert_limit` (3 active certificates already), `429 rate_limited` (`CERT_ISSUES`: 10
certificates per user per hour, app and web together; a refused request is not counted),
`401`, `503 unavailable` (database, or the Device CA files cannot be read).

### `GET /certs`
Response `200`:
```json
{
  "limit": 3,
  "certs": [
    {"serial": "4f1c0e...", "label": "Pixel 8", "issued_at": "...", "not_after": "...",
     "revoked_at": null, "revoke_reason": null, "via": "app", "active": true}
  ]
}
```
- Only the token's user. Newest first, revoked and expired certificates included.
- `via` is `"app"` (CSR from the Android app) or `"web"` (PKCS#12 from `/certs`).
- `revoke_reason` is `"user"`, `"not_me"`, `"admin"` or `"password"` (password change), or `null`.
- `active` is `true` when the certificate is not revoked and not expired.

Errors: `401`, `503 unavailable`.

### `DELETE /certs/{serial}`
Revokes the certificate, then sends a Disconnect-Request (the same rules and limits as
`POST /devices/disconnect`: `DISCONNECTS`, one at a time per user) for each live session of the
devices that signed in with this certificate in the last 30 days (`device_cert_seen`). A device
that is not online gets nothing.

Response `200`:
```json
{"serial": "4f1c0e...", "revoked_at": "...", "disconnect": [{"nas": "10.89.0.1", "result": "ACK"}]}
```
- `disconnect` is `[]` when no such device is online.
- A second `DELETE` of a revoked certificate gives `200` with the first `revoked_at` (and keeps
  the first reason), and tries the disconnect again.
- The revocation is written before the disconnect. After a `409` or `429` the certificate stays
  revoked; the client can repeat the `DELETE` to retry the disconnect.
- A revocation is final: no role can clear `revoked_at` again (trigger of migration 006).
- Without an `ACK`, the device is dropped at its next re-check, within `reauth_interval`
  seconds, when FreeRADIUS refuses the revoked serial.

Errors: `404 not_found` (no certificate of this user with that serial; also for a serial that is not
lower-case hex), `409 disconnect_in_progress`, `429 rate_limited`, `401`, `503 unavailable`.

### Web pages (session cookie, not the API)
| Endpoint | Path | Form fields | What it does |
|---|---|---|---|
| `pki.certs` | `GET /certs` | - | The list, revoke buttons, and the form for a new certificate |
| `pki.new` | `POST /certs/new` | `label`, `csrf_token` | Issues a certificate with `via="web"` and shows it once (below) |
| `pki.revoke` | `POST /certs/revoke` | `serial`, `csrf_token` | `revoke_core(uid, serial, "user")`, then back to `/certs` |

`POST /certs/new` is for Apple, Windows and Linux devices, which cannot make a CSR from a web page:
- The server makes an RSA 3072 key and a random passphrase (20 characters of
  `abcdefghjkmnpqrstuvwxyz23456789` in groups of 4 with dashes, about 99 bits; the dashes are part of
  it). The answer page shows the passphrase and has the PKCS#12 file as a `data:` download link
  (`nits-wifi-<uid>.p12`). The file holds the key, the certificate and the Device CA (not the root).
- The key and the passphrase exist only in memory for that one response: they are never stored,
  logged or shown again (`Cache-Control: no-store`). A user who leaves the page before installing
  the file revokes that certificate and makes a new one.
- The PKCS#12 encryption is PBE-SHA1-3DES with a SHA-1 MAC (50,000 rounds): the form that Windows
  10, macOS and iOS all import. The random passphrase, not the cipher, carries the protection.
- Errors (limit, label, rate limit, database) come back as a message on `/certs`.

### Core functions for other modules (S6)
`pki.py` is a feature module (section 8.1). Call these only when `"pki" in core.app.blueprints`.
They raise `core.PortalError` subclasses, like the core functions of `app.py`.

`pki.revoke_core(uid, serial, reason, disconnect=True)` -> `{"serial", "revoked_at", "disconnect": [{"nas", "result"}]}`
- The same core as `DELETE /certs/{serial}` and the web revoke. `reason` is `"user"`, `"not_me"`,
  `"admin"` or `"password"` (another value raises `InvalidInput`). `revoked_at` is a `datetime`
  with time zone.
- A second call returns the first `revoked_at` and keeps the first reason.
- Raises `NotFound` (no certificate of this user with that serial), `Unavailable`, and from the
  disconnect `Conflict` (`disconnect_in_progress`) or `RateLimited`; the certificate then stays
  revoked, so a caller treats those two as "revoked". It calls `core.disconnect_core` once per
  device, so it uses `DISCONNECTS`.
- `disconnect=False` only revokes (`"disconnect": []`) and never raises `Conflict` or
  `RateLimited`. "Not me" uses it, because it disconnects the device itself.

`pki.revoke_all_core(uid, reason)` -> `["4f1c0e...", ...]`
- Revokes every active certificate of the user (used by `app.password_core` with `"password"`),
  then tries to disconnect the devices that used them; a failed disconnect is only logged.
  Returns the serials it revoked. Raises `InvalidInput` (reason) or `Unavailable`.

`pki.certs_for_mac(uid, mac)` -> `["4f1c0e...", ...]`
- The serials of this user's active certificates that the device `mac` (`Calling-Station-Id`, in
  the form of `user_devices`) used to sign in during the last 30 days, most recent first. `[]` for
  a MAC that does not match `[0-9A-Za-z:.-]{1,40}`. Raises `Unavailable`.
- It reads `device_cert_seen`, which FreeRADIUS writes on every EAP-TLS Access-Accept. The portal
  never reads `radpostauth` for it.

Also available: `pki.issue_core(uid, label, via, public_key=None)` and `pki.list_core(uid)`.

### FreeRADIUS side
- `mods-available/eap`, `tls-config tls-device`: EAP-TLS needs a client certificate that chains
  through the Device CA to the root (`device-chain.pem`, made by `radius-start.sh`), issued by the
  Device CA itself (`check_cert_issuer`), with the CN equal to the EAP identity (`check_cert_cn`).
  No TLS session cache, so every login is checked again.
- `sites-available/check-eap-tls` then accepts only when: the user is in LDAP and the CN is
  exactly the stored uid; the serial is in `device_certs` for that user, not revoked, not expired
  (this table lookup is the revocation check: no CRL, no OCSP; PostgreSQL down means reject);
  and `campus_authorize` accepts (disabled, VLAN, Class, re-check interval, device limit, as for TTLS).
- `sites-available/default` (post-auth) records the serial, the uid and the `Calling-Station-Id`
  of each EAP-TLS Access-Accept in `device_cert_seen`. EAP-TTLS/PAP and PEAP are unchanged.

## 7. S6: EAP-TLS clients (`portal/downloads.py`, `portal/profiles.py`, `portal/activity.py`, `android/`)

### `GET /profiles/android?method=tls`
`method` is `ttls` (default, section 5) or `tls`. Another value (also an empty one, or another
case such as `TLS`) gets `400 invalid_input`. Without `method` the answer is the section 5
answer, unchanged.

Response `200` for `tls`:
```json
{
  "ssid": "NITS-Lab",
  "eap": "TLS",
  "phase2": null,
  "identity": "student042",
  "anonymous_identity": null,
  "domain_suffix_match": "radius.nitsrinagar.lab",
  "alt_subject_match": "DNS:radius.nitsrinagar.lab",
  "ca_pem": "-----BEGIN CERTIFICATE-----\n..."
}
```
- `identity` is the uid, the CN of the device certificate (section 6).
- The answer does not depend on `pki.py`: without it, the app gets this answer, and then
  `POST /certs` gives `404`.

Errors: `400 invalid_input`, `401`, `503 unavailable` (the CA file cannot be read).

The app (`android/`, `core/Tls.kt`):
1. makes an EC P-256 key pair on the phone and a PKCS#10 CSR (`SHA256withECDSA`, subject CN = uid);
2. calls `POST /certs` with the CSR and a label (the phone model, 1 to 40 characters);
3. checks the answer (the same public key, not a CA, valid now, clientAuth, signed by the
   Device CA in `chain_pem`), and revokes the certificate at once (`DELETE /certs/{serial}`)
   when the check fails;
4. calls `setClientKeyEntryWithCertificateChain(key, [cert_pem, Device CA])` with
   `Eap.TLS`, `setIdentity(identity)`, `setCaCertificate(ca_pem)`,
   `setDomainSuffixMatch` and `setAltSubjectMatch`;
5. revokes the certificate when Android did not save the network (the key is gone).

The key is a software key in memory, not an AndroidKeyStore key:
`WifiEnterpriseConfig.setClientKeyEntry*` sends the key to the Wi-Fi service as PKCS#8 bytes
(`PrivateKey.getEncoded()`), which an AndroidKeyStore key does not give, and
`setClientKeyPairAlias` needs a KeyChain key that a device policy owner granted to Wi-Fi. The app
never writes the key to a file, preferences, a `Bundle`, a log or a backup. `409 cert_limit` is
shown as "You already have 3 active device certificates ... Revoke the certificate of a device
that you no longer use".

### EAP-TLS web profiles (`downloads.tls_profile`, for the `/certs` page of S5)
`downloads.py` has no route for these files: the PKCS#12 file exists only in the request of the
`/certs` page (section 6) that makes it. That page calls one of:

```python
downloads.tls_profile(uid, kind, p12)   # -> (body: bytes | str, filename, mimetype)
downloads.tls_download(uid, kind, p12)  # -> flask.Response, Content-Disposition: attachment
```
- `uid` is the logged-in user, `p12` the PKCS#12 file (DER bytes) that `pki.py` just made, with the
  device certificate, its key and the Device CA, encrypted with the passphrase that the page shows.
  The passphrase is never passed and never put in a file: the device asks for it.
- `kind` and the file:

  | `kind` | File name | MIME type | Contents |
  |---|---|---|---|
  | `apple` | `nits-wifi-tls.mobileconfig` | `application/x-apple-aspen-config` | root CA, `com.apple.security.pkcs12` (no `Password`), `com.apple.wifi.managed` with `AcceptEAPTypes [13]`, `PayloadCertificateUUID` of the PKCS#12 payload, `UserName` uid, `TLSTrustedServerNames`, the CA anchor. CMS-signed when `PROFILE_SIGNING=yes`. |
  | `windows` | `nits-wifi-tls-setup.ps1` | `text/plain; charset=utf-8` | imports the PKCS#12 into `Cert:\CurrentUser\My` (`Import-PfxCertificate`, passphrase from `Read-Host -AsSecureString`, key not exportable), adds the root CA (`certutil -user`), adds a WLAN profile for EAP-TLS (type 13, `ServerNames`, `TrustedRootCA` SHA-1 thumbprint, no prompt). |
  | `linux` | `nits-wifi-tls-setup.sh` | `application/x-sh` | writes the CA and `~/.local/share/nits-wifi/device.p12` (mode 600), `nmcli` with `802-1x.eap tls`, `client-cert` and `private-key` = the PKCS#12 file, `private-key-password-flags 2` (the desktop asks), `domain-suffix-match`. |

- Errors: `core.InvalidInput` (unknown `kind`, or `p12` is not DER of a sane size, at most 16 KB),
  `core.Unavailable` (the CA cannot be read, or `PROFILE_SIGNING=yes` and the signing files
  cannot be read: never an unsigned profile in place of a signed one).
- The portal logs `profile download: uid=<uid> kind=tls-<kind>`, never the content. The response
  has `Cache-Control: no-store` like every portal response.
- The pure builders are `profiles.apple_tls_mobileconfig(s, p12)`, `profiles.windows_tls_ps1(s, p12)`,
  `profiles.windows_tls_wlan_xml(s)` (no key: the certificate comes from the user's store),
  `profiles.linux_tls_nmcli(s, p12)` and `profiles.android_tls_settings(s)`.
- `pki.new` (web `POST /certs/new`) calls `tls_profile` for `apple`, `windows` and `linux` and puts
  each file on the page as a `data:` download next to the `.p12`, in the same response (the key
  is never kept). A file that cannot be made is left out; the page and the `.p12` still work.
- Not verified on real devices yet (Apple, Windows, Linux): see the S6 PR.

### "Not me" revokes the device's certificates (`POST /alerts/{mac}`, web `/activity/review`)
When `pki` is loaded (`"pki" in core.app.blueprints`), `"not_me"` (section 4), after the verdict is
recorded and before the disconnect:
1. `pki.certs_for_mac(uid, mac)`: the serials of the user's active certificates that this MAC
   used to sign in during the last 30 days (section 6);
2. `pki.revoke_core(uid, serial, "not_me", disconnect=False)` for each serial: the review then
   disconnects the device once. `Conflict` or `RateLimited` from it means "revoked" (section 6).

A failure in these calls is logged; it never undoes the verdict, never stops the disconnect, and
the client still opens the password change. The `POST /alerts/{mac}` answer has two added fields:

```json
{"mac": "DE-AD-BE-EF-00-01", "verdict": "not_me", "disconnect": [], "next": "password",
 "revoked": ["4f1c0e"], "revoke_failed": []}
```
- `revoked`: the serials that were revoked. `revoke_failed`: the serials that could not be
  revoked, or `["*"]` when the list of serials could not be read. The user then revokes on the
  `/certs` page or in the app.
- Both are `null` for `"me"`, and for `"not_me"` when `pki` is not loaded.
- On `409` or `429` from the disconnect, the revocation has already run.

## 8. Notes for the stages that build on S0

### 8.1 Feature modules
- `app.register_features()` (end of `portal/app.py`) loads each of these modules
  if its file exists: `apiauth`, `api`, `activity`, `downloads`, `pki`. Each
  module has one Flask Blueprint called `bp`. The Dockerfile copies `*.py`.
- A module imports `app as core` and calls the core functions:
  `core.login_core`, `core.device_overview`, `core.disconnect_core`,
  `core.password_core`. They raise `core.PortalError` subclasses with `status`,
  `code` and `message`. `apiauth.portal_error(exc)` turns one into the error
  response.
- Every view under `/api` must have `@apiauth.api_auth_required`, which sets
  `flask.g.api_user = {"uid", "dn", "version", "student"}`. A view under `/api`
  without it (or `@apiauth.api_public`, only for the token endpoint) is refused
  with `401` (fail closed), for every method. Do not use these decorators on a
  view outside `/api`: it is refused with `500`. Use `apiauth.api_error(status,
  code, message)` for other errors and `apiauth.json_body()` to read a request.
- Web pages use `@core.login_required` and keep CSRF tokens in their forms.
